סיפור הקוד — זרימת OCR (סריקה)

כיצד תמונת ספר הופכת למילים בבסיס הנתונים

הסיפור המלא: מצלמה → מסך → Room
  1. 1
    ScanFragment נטען. CameraX מאתחל שני UseCases: Preview (מה שהמשתמש רואה) ו-ImageCapture (לצילום). שניהם מחוברים ל-ProcessCameraProvider.bindToLifecycle().
  2. 2
    המשתמש לוחץ "צלם". imageCapture.takePicture() שומר את התמונה לקובץ זמני. ה-callback מוקרא עם File על CameraX background thread.
  3. 3
    loadRotatedBitmap(file). קורא את EXIF הכיוון של הקובץ דרך ExifInterface. המצלמה שומרת בlandscape עם EXIF. ללא תיקון — התמונה מסובבת. יוצר Matrix עם setRotate(degrees) ומייצר Bitmap מסובב.
  4. 4
    מעבר למצב REVIEW. מסתיר את ה-PreviewView, מציג ImageView עם הBitmap המתוקן. UI עובר לstate של "סקירה" — כפתורי "אשר" ו"צלם שוב" מופיעים.
  5. 5
    ML Kit Text Recognition. TextRecognition.getClient() מנתח את ה-Bitmap באמצעות OCR מקומי (on-device, ללא אינטרנט). מחזיר Task<Text>.
  6. 6
    עיבוד תוצאות OCR.
    • מצב ספר (extractWordBoxes): עובר על TextBlock → Line → Element. לכל Element — חותך bounding box מה-Bitmap המקורי → Bitmap מילה קטנה.
    • מצב טקסט חופשי (extractFreeTextBoxes): חותך שורות שלמות.
  7. 7
    ML Kit Translate. TranslationModel(EN→HE). קודם בודק אם מודל ההורדה קיים (downloadModelIfNeeded()). לאחר הורדה ראשונה — עובד offline. מתרגם כל מילה/שורה.
  8. 8
    תצוגת תוצאות. RecyclerView מציג זוגות (אנגלית, עברית). המשתמש בוחר אילו מילים לשמור.
  9. 9
    שמירה ל-Room. המילים הנבחרות עוברות דרך WordRepository.insert(word) → executorService.execute() → WordDao.insert(word). מסומנות כ-isVerified=false, isFavorite=true (מילים אישיות).

סיפור הקוד — זרימת הגמיפיקציה (XP)

כיצד תשובה נכונה הופכת ל-XP, Level ו-Streak

הסיפור: ממשתמש עונה נכון → עדכון UI
  1. 1
    המשתמש בוחר תשובה נכונה ב-QuizFragment. נרשמים שני ערכים: beforeMastery = word.getMasteryLevel() לפני עדכון.
  2. 2
    עדכון Word בDB. word.setCorrectAttempts(word.getCorrectAttempts() + 1) ו-word.setTotalAttempts(...+1). afterMastery = word.getMasteryLevel() מחושב לאחר עדכון.
  3. 3
    GamificationEngine.onCorrectAnswer(beforeMastery, afterMastery). מוסיף +10 XP תמיד. אם beforeMastery < 5 AND afterMastery == 5 → בונוס +100 XP (הגיע לשליטה מלאה!).
  4. 4
    Level מחושב מחדש. L = floor(sqrt(totalXp / 100)) + 1. אם Level עלה — מוצג animation חגיגי.
  5. 5
    כפול כתיבה (Dual-Write). GamificationEngine מעדכן גם SharedPreferences (מיידי, לוקאלי) וגם Firestore users/{uid} (לענן).
  6. 6
    אנימציית +10 XP. ב-QuizFragment: tvXpGain.setVisibility(VISIBLE), ObjectAnimator מפעיל אנימציית עלייה ו-Fade Out.
  7. 7
    Handler.postDelayed(1000ms). לאחר שנייה — מתקדמים לשאלה הבאה. לא Thread.sleep שיקפיא את ה-UI!
נוסחאות הגמיפיקציה
Mastery = min(5, floor(correctAttempts / (totalAttempts + 1) × 5))
Level = floor(sqrt(totalXP / 100)) + 1
XP_for_next_level = ((Level)²) × 100
+1 במכנה של Mastery: מונע חלוקה באפס כאשר totalAttempts = 0. גם מבטיח שמשתמש עם ניסיון אחד נכון מ-1 לא יקבל Mastery=5 מיד.

סיפור הקוד — זרימת סנכרון Firebase

כיצד מילים מ-Firestore מגיעות ל-Room בלי למחוק נתוני תרגול

אלגוריתם Insert-Only — הסיפור
  1. 1
    MyWordsViewModel בודק throttle של 24 שעות. קורא SharedPreferences "last_global_sync_ms". אם עברו פחות מ-24 שעות — לא מסנכרן.
  2. 2
    WordRepository.syncGlobalWordsFromFirestore(). מבצע firestore.collection("words").get() — מוריד את כל 1902 המילים.
  3. 3
    קבלת מילים קיימות מ-Room. ב-background thread: wordDao.getAllWordsSnapshot() (query סינכרוני, לא LiveData). בונה Set<String> existingEnglishWords.
  4. 4
    השוואה ו-Insert בלבד. לכל מילה מ-Firestore: if (!existingEnglishWords.contains(word.englishWord)) → מכניס ל-Room. מילים קיימות — לא נגעות. כך כל נתוני התרגול (correctAttempts, errorInQuiz וכד') נשמרים.
  5. 5
    Room משדר LiveData. כי הכנסנו שורות חדשות → Room מעיר את ה-Observer ב-Fragment → RecyclerView מתעדכן אוטומטית.
  6. 6
    עדכון timestamp. SharedPreferences.edit().putLong("last_global_sync_ms", System.currentTimeMillis()).apply() — הסנכרון הבא יהיה עוד 24 שעות.
מדוע Insert-Only? — הבעיה שנפתרה
בעיה קודמת: הקוד המקורי ביצע deleteUnmarkedGlobalWords() ואז insert() לכל המילים מחדש. כל פעם שהמשתמש ניווט למסך המילים, כל 1902 המילים נמחקו ונוספו מחדש — תוך כדי מחיקת correctAttempts, totalAttempts, errorInQuiz וכו'.
הפתרון (Insert-Only): אנחנו לעולם לא מוחקים מילים גלובליות שכבר קיימות. רק מוסיפים מילים חדשות שטרם היו. נתוני התרגול נשמרים לעולם.

מתודות מרכזיות
getMasteryLevel() : int ▶

מחשב רמת שליטה בין 0 ל-5 בהתבסס על ביצועי המשתמש.

M = min(5, floor(correctAttempts / (totalAttempts + 1) × 5))

הסבר: totalAttempts + 1 במכנה — מניעת חלוקה באפס. כפל ב-5 ממיר יחס (0-1) לסקאלה (0-5). min(5,...) מוודא שלא חורגים מ-5.

public int getMasteryLevel() {
    return Math.min(5,
        (int) (correctAttempts / (totalAttempts + 1.0) * 5));
}

דוגמאות:

  • correctAttempts=0, totalAttempts=0 → min(5, floor(0/1×5)) = 0
  • correctAttempts=3, totalAttempts=3 → min(5, floor(3/4×5)) = min(5,3) = 3
  • correctAttempts=5, totalAttempts=5 → min(5, floor(5/6×5)) = min(5,4) = 4
  • correctAttempts=10, totalAttempts=10 → min(5, floor(10/11×5)) = min(5,4) = 4
  • correctAttempts=20, totalAttempts=20 → min(5, floor(20/21×5)) = min(5,4) = 4
  • correctAttempts=100, totalAttempts=100 → ≈ 4 → צריך יחס כמעט 1.0 ל-5

פינת הבוחן — זאב פריימן: Word.java
מדוע יש +1 במכנה של נוסחת getMasteryLevel?
כדי למנוע חלוקה באפס כאשר totalAttempts = 0 (מילה חדשה שעוד לא תורגלה). בלי ה-+1, הנוסחה היתה 0/0 = NaN — שגיאה בחישוב. ה-+1 גם מבטיח שמשתמש עם תשובה נכונה אחת מ-1 לא ישיג Mastery=5 מיד (1/2×5=2.5 → floor=2, לא 5).
מה ההבדל בין isFavorite ל-isVerified?
isVerified=true — מילה גלובלית שנוספה מ-Firestore ועברה אימות על ידי האדמין. isFavorite=true — מילה שהמשתמש סימן כאישית (נסרקה בOCR, נוספה ידנית, או סומנה). מילה אישית: isVerified=false AND isFavorite=true. הסינון ב-getPersonalWords() מבוסס על שני השדות האלה.
מדוע creationTimestamp הוא long ולא Date?
Room לא יודע לאחסן java.util.Date ישירות בלי TypeConverter. Unix timestamp (milliseconds since epoch) הוא long — Room מאחסן אותו ישירות. ה-DashboardFragment משתמש בו לחישוב גרף שבועי: מחסיר את ה-timestamp של יומיים אחורה ומונה כמה מילים נוספו בכל יום.
מדוע errorInQuiz, errorInSpelling, errorInFlashcards שדות נפרדים ולא מחושבים?
כי השגיאה האחרונה בכל מודול היא מידע סטטוס — לא ניתן לחשב אותה מ-correctAttempts כי אלה ספירות מצטברות. לדוגמה, מילה עם correctAttempts=10, totalAttempts=12 — ייתכן שהשתי הטעויות היו לפני חודש. ה-errorInQuiz מציין שהמשתמש טעה בפעם האחרונה בחידון — זה מה שנראה כ"טעויות אחרונות" ב-PracticeFragment.

פינת הבוחן — זאב פריימן: WordDao.java
מדוע getAllWords() מחזיר LiveData ולא List?
כי Room מטמיע Observer Pattern: כשה-DAO מחזיר LiveData, Room שומר observer על הטבלה. כל פעם שמוכנסת/מעודכנת/נמחקת שורה — Room דוחף את הנתונים החדשים לכל ה-Observers. ה-Fragment לא צריך לשאול מחדש, לא צריך Polling, הUI מתעדכן אוטומטית. אם היה מחזיר List, ה-Fragment היה צריך לשאול שוב בכל שינוי — מורכבות וסיכון לBugs.
מה OnConflict=REPLACE עושה בדיוק?
אם נוסיף Word עם id שכבר קיים בטבלה — Room מוחק את השורה הישנה ומכניס את החדשה. זה דורש זהירות: אם insertים דרך Firestore מביאים Word עם id=0 (כי בנינו אובייקט חדש), Room מייצר id חדש ולא מחליף. ה-REPLACE מגן מפני שגיאת UNIQUE constraint אבל לא כלי לעדכון — לזה יש @Update.
מדוע ה-DAO הוא interface ולא class?
Room מייצר בזמן קומפילציה (Annotation Processing) את המימוש הקונקרטי של הממשק — קוד Java שמריץ SQL ומחזיר את הנתונים. המפתח כותב רק את ה-contract (ממשק + SQL). אם Room היה מחייב class, המפתח היה צריך לכתוב boilerplate קוד של גישה ל-SQLite — בדיוק מה ש-Room אמור להחליף.

public abstract class WordRoomDatabase extends RoomDatabase {

    private static volatile WordRoomDatabase INSTANCE; // volatile!

    public static WordRoomDatabase getDatabase(Context context) {
        if (INSTANCE == null) {                  // בדיקה ראשונה
            synchronized (WordRoomDatabase.class) {
                if (INSTANCE == null) {          // בדיקה שנייה
                    INSTANCE = Room.databaseBuilder(
                        context.getApplicationContext(),
                        WordRoomDatabase.class,
                        "word_database"
                    )
                    .fallbackToDestructiveMigration()
                    .build();
                }
            }
        }
        return INSTANCE;
    }

    public abstract WordDao wordDao();
}
Double-Checked Locking: שתי בדיקות if (INSTANCE == null). הראשונה — ביצועים (לא נכנסים ל-synchronized אם כבר קיים). השנייה — בטיחות (Thread שמחכה על ה-lock לא ייצור instance נוסף).
מדוע volatile? בלי volatile, ה-JVM יכול לשמור את הערך ב-CPU cache של Thread מסוים. Thread אחר יראה null גם אחרי ש-Thread ראשון כבר יצר את ה-instance. volatile מבטיח שהכתיבה לזיכרון נראית לכל ה-threads מיד.
פינת הבוחן — זאב פריימן: WordRoomDatabase.java
מדוע Double-Checked Locking ולא synchronized על כל המתודה?
אם כל המתודה היתה synchronized, כל קריאה ל-getDatabase() — גם לאחר שה-instance כבר נוצר — היתה ממתינה ל-lock. זה bottleneck ביצועים. Double-Checked Locking: רק בפעם הראשונה (כשINSTANCE==null) נכנסים לסינכרון. אחר כך, כל קריאות קוראות ישירות מ-memory ללא נעילה.
מה עושה fallbackToDestructiveMigration?
כשגרסת ה-DB (version=3) לא תואמת את הDB הישן שעל המכשיר — Room לא יודע כיצד לשדרג את הסכמה. ללא fallback, האפליקציה קורסת. עם fallbackToDestructiveMigration() — Room מוחק את הDB הישן ומייצר חדש. מחיר: נתוני המשתמש הישנים אובדים. פתרון אמיתי: לכתוב Migration מפורש, אבל עבור שלב הפיתוח זה פתרון מקובל.
מדוע abstractWordRoomDatabase abstract class ולא class רגיל?
Room מייצר בזמן קומפילציה את המחלקה הקונקרטית (WordRoomDatabase_Impl). המחלקה האבסטרקטית היא ה-contract: "כאן יש DAO מסוג WordDao". Room משלים את המימוש. אם היתה class רגיל — Room לא יכול היה לדרוס את המתודות.

מדוע ExecutorService עם 4 threads ולא Thread ישיר?
יצירת Thread חדש לכל פעולה יקרה בזיכרון וב-CPU — יצירת Thread עצמה לוקחת זמן ומשאבים. ExecutorService מנהל מאגר (pool) של 4 threads שנוצרו מראש. פעולת DB חדשה מוסיפה task לתור — thread פנוי לוקח אותו. 4 threads מספיקים לעומס DB טיפוסי ולא מכבידים על מעבד מכשיר מוביילי.
למה ה-Repository הוא "Single Source of Truth"?
הRepository מחליט מאיפה הנתונים באים — Room, Firestore, או שניהם. ה-ViewModel לא יודע. אם מחר נחליף Room ב-SQLDelight, נשנה רק ב-Repository. ה-ViewModel וה-Fragment נשארים ללא שינוי. זה עיקרון Separation of Concerns — כל מחלקה אחראית על דבר אחד בלבד.
מדוע syncGlobalWordsFromFirestore מבצע query סינכרוני ל-Room ב-background thread?

    super(application);
    repository = new WordRepository(application);
    allWords = repository.getAllWords();
    personalWords = repository.getPersonalWords();
    sharedPrefs = application.getSharedPreferences(
        "app_prefs", Context.MODE_PRIVATE);

    boolean migrated = sharedPrefs.getBoolean(
        "personal_words_migration_v1", false);
    if (!migrated) {
        repository.deleteUnmarkedGlobalWords();
        sharedPrefs.edit().putBoolean(
            "personal_words_migration_v1", true).apply();
    }

    // Throttle 24 שעות:
    long lastSync = sharedPrefs.getLong("last_global_sync_ms", 0);
    long now = System.currentTimeMillis();
    if (now - lastSync > 24 * 60 * 60 * 1000L) {
        syncFromCloud();
        sharedPrefs.edit().putLong("last_global_sync_ms", now).apply();

private List<Word> buildQuestionList(List<Word> all) {
    List<Word> hard = new ArrayList<>();   // Mastery 0-2
    List<Word> fresh = new ArrayList<>();  // totalAttempts == 0
    List<Word> solid = new ArrayList<>();  // Mastery 3-5

    for (Word w : all) {
        int m = w.getMasteryLevel();
        if (w.getTotalAttempts() == 0) fresh.add(w);
        else if (m <= 2) hard.add(w);
        else solid.add(w);
    }

    Collections.shuffle(hard);
    Collections.shuffle(fresh);
    Collections.shuffle(solid);

    List<Word> result = new ArrayList<>();
    addUpTo(result, hard, (int)(SESSION_SIZE * 0.6));  // 12
    addUpTo(result, fresh, (int)(SESSION_SIZE * 0.2)); // 4
    addUpTo(result, solid, SESSION_SIZE - result.size()); // נשאר

    if (result.size() < SESSION_SIZE) {
        // ממלא מהנשאר אם אין מספיק
    }
    Collections.shuffle(result);
    return result;
}

מדוע currentAttempted flag נאפס לכל מילה חדשה?
ה-flag הוא per-question state. כשקוראים nextWord(), מאפסים: currentAttempted = false. כך כל מילה חדשה מתחילה עם flag נקי, ומאפשר לספור ניסיון ראשון מחדש. בלי האיפוס — אחרי מילה ראשונה, שום מילה נוספת לא תספור totalAttempts.
מה QUEUE_FLUSH ב-TTS.speak?
TTS מנהל queue של הודעות לקריאה. QUEUE_FLUSH מנקה את כל ה-queue ומתחיל ישירות בהודעה החדשה. QUEUE_ADD היה מחכה עד שהקריאה הנוכחית תסתיים. QUEUE_FLUSH מתאים כאן כי אנחנו רוצים שהמילה החדשה תיאמר מיד, אפילו אם TTS באמצע אמירה של המילה הקודמת.

מדוע layoutBack מקבל rotationY=180 מראש ולא בזמן האנימציה?
layoutBack מוגדר ב-XML או ב-onCreate עם rotationY=180°. כך הוא תמיד "counter-rotated". כשה-card container ב-0° — layoutBack (שמוסתר) ב-180° = מסובב, לא נראה. כשה-card ב-180° — layoutBack ב-360°=0° = ישר. האנימציה רק מסובבת את ה-container — הCounter-rotation קבוע ולא חלק מהאנימציה.

private Bitmap loadRotatedBitmap(File file) {
    Bitmap bitmap = BitmapFactory.decodeFile(file.getAbsolutePath());
    ExifInterface exif = new ExifInterface(file.getAbsolutePath());
    int orientation = exif.getAttributeInt(
        ExifInterface.TAG_ORIENTATION,
        ExifInterface.ORIENTATION_NORMAL);

    int degrees = 0;
    switch (orientation) {
        case ORIENTATION_ROTATE_90:  degrees = 90;  break;
        case ORIENTATION_ROTATE_180: degrees = 180; break;
        case ORIENTATION_ROTATE_270: degrees = 270; break;
    }

    if (degrees == 0) return bitmap;
    Matrix m = new Matrix();
    m.setRotate(degrees);
    return Bitmap.createBitmap(bitmap, 0, 0,
        bitmap.getWidth(), bitmap.getHeight(), m, true);
}

public void syncFromFirestore(Runnable callback) {
    String uid = FirebaseAuth.getInstance()
        .getCurrentUser().getUid();

        .get()
        .addOnSuccessListener(doc -> {

}

public static int computeStreak(String lastDate, String today) {
    if (lastDate == null) return 1; // יום ראשון

    long daysDiff = daysBetween(lastDate, today);

    if (daysDiff == 0) {
        return currentStreak; // אותו יום — אל תשנה
    } else if (daysDiff == 1) {
        return currentStreak + 1; // יום רצוף!
    } else {
        return 1; // יותר מיום — איפוס לאחד
    }
}

private static long daysBetween(String d1, String d2) {
    SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd", Locale.US);
    Date date1 = sdf.parse(d1);
    Date date2 = sdf.parse(d2);
    long diff = date2.getTime() - date1.getTime();
    return TimeUnit.DAYS.convert(diff, TimeUnit.MILLISECONDS);
}

private void calculateMastery(List<Word> words) {
    int total = words.size();
    int mastered = 0;
    long totalCorrect = 0, totalAttempts = 0;

    for (Word w : words) {
        if (w.getCorrectAttempts() >= 3) mastered++;
        totalCorrect += w.getCorrectAttempts();
        totalAttempts += w.getTotalAttempts();
    }

    int masteryPct = total == 0 ? 0 : mastered * 100 / total;
    int accuracy = totalAttempts == 0 ? 0 :
        (int)(totalCorrect * 100 / totalAttempts);

    updateRank(masteryPct, mastered);
}

עקרונות ארכיטקטורה — לבוחן

10 שאלות ותשובות מרכזיות על עיצוב המערכת

מדוע AndroidViewModel ולא ViewModel?

ה-ViewModel הרגיל לא מקבל Application context. אנחנו צריכים Application context ל: (1) Room.databaseBuilder — יצירת DB. (2) SharedPreferences — קריאת/כתיבת הגדרות. Application context בטוח — חי כמו האפליקציה עצמה, לא קשור ל-Activity שנהרסת בסיבוב מסך. שימוש ב-Activity context ב-ViewModel = Memory Leak בטוח.

מדוע LiveData מ-Room ולא List רגיל?

LiveData + Room = Observer Pattern מובנה. Room מחזיק Observer על הטבלה. שינוי בטבלה → Room דוחף נתונים חדשים → LiveData מעדכן → Fragment מקבל → RecyclerView מצייר מחדש. ללא זה: Fragment היה צריך לשאול מחדש בכל שינוי (Polling) — גוזל סוללה, מורכב לתחזוקה, ומועד לבאגים.

מדוע אלגוריתם Insert-Only בסנכרון?

מחיקה+הכנסה מחדש = איפוס correctAttempts, totalAttempts, errorInQuiz וכל נתוני התרגול. המשתמש יאבד את כל ההתקדמות שלו. Insert-Only מוסיף רק מילים שעוד לא קיימות — נתוני המשתמש הקיימים נשמרים לעולם. זה ה-bug הגדול שתוקן בגרסה הנוכחית (עם throttle 24 שעות).

מדוע Double-Checked Locking ב-Singleton?

Singleton רגיל עם synchronized על כל getMtodה — כל קריאה ממתינה ל-lock גם כשinstance כבר קיים. DCL: בדיקה ראשונה בלי lock (מהיר), בדיקה שנייה עם lock (בטוח). volatile מבטיח visibility בין threads — בלי volatile, JVM instruction reordering עלול לגרום ל-Thread לקרוא instance לא מוגדר לחלוטין.

מדוע binding=null ב-onDestroyView?

Fragment object חי יותר מה-View שלו. כשה-View נהרס (onDestroyView) — ה-Fragment עדיין חי (בback stack). ViewBinding מחזיק reference לכל ה-Views. אם לא מנקים → binding מחזיק → Views לא יכולים להישחרר על ידי GC → Memory Leak. בכל חזרה לFragment = View חדש + binding חדש. הכלל: binding = null ב-onDestroyView תמיד.

מדוע Handler.postDelayed ולא Thread.sleep?

Thread.sleep() על Main Thread — קופא את Looper. לא מעבד Events, לא מצייר UI, לא מגיב ל-Touch. אחרי 5 שניות → ANR Dialog. Handler.postDelayed() — מוסיף Message לLooper עם delay. ה-Looper ממשיך לעבד Events אחרים בינתיים. אחרי delay — מריץ ה-Runnable. UI זורם, UX חלק.

מדוע ExifInterface לתיקון תמונת מצלמה?

Camera sensor מצלם בlandscape (לכן הרזולוציה גבוהה). כשמחזיקים טלפון ב-portrait ומצלמים, החומרה מוסיפה EXIF metadata: "סובב תמונה זו 90°". ImageView רגיל לא קורא EXIF — מציג בlandscape (מסובב). ExifInterface קורא את הsorientation → Matrix מסובב → Bitmap נכון.

מדוע throttle 24 שעות לסנכרון Firestore?

כל ניווט ל-MyWordsFragment (ב-bottom nav) הפעיל onCreate → ViewModel נוצר מחדש → syncFromCloud() נקרא. כל sync = download של 1902 documents מFirestore + כתיבתם ל-Room. עם מחיקה+הכנסה (הbug הקודם) = איפוס נתוני תרגול. Throttle מגביל ל-1 פעם ב-24 שעות — חוסך bandwidth, מגן על נתונים, שיפור ביצועים.

מדוע ExecutorService עם 4 threads?

Room מאסר גישה מMain Thread (throws IllegalStateException). Thread pool מנהל 4 threads שנוצרו מראש — יעילים יותר מיצירת Thread חדש לכל פעולה. 4 threads = מספיק לpractice modules שמריצים מספר DB writes בסשן, לא יותר מדי שלא יכביד על CPU מוביילי.

למה 60/20/20 ב-Quiz?

Spaced Repetition: מילים קשות (Mastery 0-2) צריכות חזרה תכופה — 60%. מילים חדשות (0 ניסיונות) צריכות היכרות ראשונית — 20%. מילים שנרכשו (3-5) צריכות maintenance לטווח ארוך — 20%. מחקר פסיכולוגי של למידה מראה שזוהי חלוקה אופטימלית לשימור ומידת למידה.
